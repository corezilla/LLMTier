## 1. 目标、范围与交付产品

本计划把V0.3设计转化为两个顺序Gate：

1. **Gate C — 编码与调试完成**：完成全部目标代码、开发期Fake Provider和冒烟调试；不以冒烟结果替代正式单元测试。
2. **Gate U — 单元测试完成**：下一阶段按冻结清单实现并运行完整单元测试。

当前只执行Gate C。Gate C通过后向用户报告准确文件数、接口数、调试场景数和剩余问题，再由用户进入Gate U。
本计划不授权production credential、真实收费probe、部署、三方联调或`runtime_activation=true`。

基线事实：仓库当前有39个`src/`生产文件（38 Python、1 HTML），主要属于legacy实现；它们不计为V0.3完成量。
V0.3本轮固定为25个生产代码文件和2个调试工具文件，共27个编码交付项。另修改`pyproject.toml`与`README.md`，
但配置/文档不计入代码文件完成率。

## 2. 生命周期模型与开发方法

采用顺序增量实现，不按目录批量造空壳：每个里程碑必须形成可启动、可观察的纵向切片。开发期间允许使用Fake Provider、
导入检查、编译检查、HTTP冒烟和浏览器人工调试；这些结果统一标记`DEBUG PASS`，不能记为`UNIT PASS`。

实现只增加`src/llmtier_v03/`目标包；legacy入口在Gate C期间继续保留但不得成为V0.3 fallback。目标入口默认不激活，
只有显式开发参数可在loopback测试环境启动。配置沿用`config/settings.json`首次bootstrap和`state/`运行状态路径，
不增加第二配置authority。

## 3. 组织、职责和 authority

- 用户：确认阶段目标与Gate转换。
- LLMTier：实现、调试、缺陷登记、进度报告和本项目提交。
- OpenAPI/fixtures：外部字段authority；实现不得自行增加endpoint/header/schema。
- 系统设计、core module和Runtime ISD：内部职责与持久化顺序authority。
- Piko/Slinky：本轮不承担编码；后续只消费已冻结标准接口并在联调阶段验证。

## 5. 需求、设计、实现与集成方法

实现顺序由持久化安全决定：store提交unknown obligation后才能provider dispatch；Admin写先验证权限与If-Match；
Responses只实现固定Pi实际消费的SSE subset；Embedding只实现已冻结表示；Web UI最后接入已经稳定的Admin API。

每个代码文件状态只允许`Planned → In Progress → Debug PASS → Unit PASS`。Gate C完成时25个生产文件和2个调试文件必须全部为
`Debug PASS`；`Unit PASS`保留给下一阶段。半成品、仅有stub、只有happy path或未接真实模块的页面都不得计为完成。

## 6. Coding/RTL/Documentation Standards

- Python 3.11+，标准库优先；新增第三方依赖需先说明必要性、许可和兼容影响。
- 所有外部字段由OpenAPI生成或显式映射；拒绝未知字段。
- 不记录Secret、Authorization、Prompt、Response、Reasoning正文或Embedding向量。
- SQLite mutation使用显式事务，关键崩溃边界在代码注释中引用ISD步骤。
- 前端使用原生HTML/CSS/JavaScript，不增加第二Web框架、登录系统或配置路径。
- legacy代码不得被复制进新包后改名充数；复用必须明确其V0.3职责并消除旧fallback语义。

## 7. Toolchain、环境、版本与可重复构建

- Python：`>=3.11`；包入口由`pyproject.toml`统一。
- SQLite：Python标准库；migration只来自`001_initial.sql`。
- 开发HTTP/Fake Provider只绑定loopback，使用临时state目录，不读取或输出真实credential。
- 每个里程碑运行`compileall`、目标包import、OpenAPI/JSON解析、contract semantic validator、现有测试和`git diff --check`。
- 调试证据记录命令、退出码、摘要和时间；不保存生产payload。

## 8. Review、Verification、Validation 与 Gate

### 8.1 Gate C 调试场景（16）

1. 空SQLite显式bootstrap成功；2. bootstrap失败完全回滚；3. 重启忽略settings变化；4. 固定Tier不可删除；
5. 云后端添加/修改；6. 本地后端添加/修改；7. ETag stale返回412；8. 引用冲突返回409；
9. health刷新不调用模型；10. 授权probe成功/失败/未知；11. exact Tier三后端路由且不跨Tier；
12. Responses文本/tool/refusal标准SSE；13. Provider 429/502/timeout；14. Embeddings float/base64/space；
15. Usage unknown→measured替换且不相加；16. 三页Web UI刷新、重启和日志脱敏。

16/16通过且27/27文件为`Debug PASS`才可宣布编码与调试完成。

### 8.2 下一阶段Gate U固定单元测试清单（18文件、至少114 cases）

下一阶段才新增`tests/v03/`：`__init__.py`、`fakes.py`及以下16个测试模块：

`test_store.py`、`test_registry.py`、`test_routing.py`、`test_models.py`、`test_responses.py`、`test_sse.py`、
`test_embeddings.py`、`test_usage.py`、`test_admin.py`、`test_health.py`、`test_audit.py`、`test_logs.py`、
`test_auth.py`、`test_errors.py`、`test_app_startup.py`、`test_webui_contract.py`。

114是最低计划数，不含现有34项静态/契约测试。Gate U要求新增用例全部通过、现有测试不回归、覆盖所有错误分支和事务边界；
测试文件存在但没有有效断言不得计数。浏览器E2E、真实provider capture和三方联调属于Gate U之后，不混入单元测试完成率。

## 9. 配置、变更、问题和缺陷管理

每个里程碑单独提交。缺陷登记必须包含复现步骤、期望/实际、所属文件和阻塞级别。设计或OpenAPI差异立即暂停相关代码，
先走设计变更；不得用代码兼容分支绕过。用户可见进度每次按以下格式报告：

```text
Gate C：x / 27代码文件Debug PASS
当前里程碑：Cx（完成项 / 总项）
调试场景：x / 16 PASS
现有静态测试：x / 34 PASS
阻塞：无或精确问题
Commit/Push：SHA或尚未提交
```

## 10. 安全、质量、供应链与第三方依赖

不读取、提交或打印`config/secrets/`、真实cookie/token、生产prompt或provider payload。Fake Provider使用合成数据。
任何新增依赖先检查版本、许可和最小必要性；当前计划不依赖外部Web框架。收费probe、credential rotation和状态变更运维
需要独立明确授权，不属于Gate C。

## 11. 发布、维护、迁移与退役

Gate C和Gate U都不执行runtime activation。legacy文件在目标包实现期间保留为未激活迁移输入；单元测试、集成和consumer联调通过后，
才制定一次性入口切换与legacy退役提交。不得长期保留两条consumer路径或运行fallback。

## 12. 度量、报告、风险与 Tailoring

核心度量为代码文件`Debug PASS`数、调试场景PASS数、未决P1/P2缺陷数和提交SHA，不使用主观百分比。
最大风险是legacy复用引入旧会话/恢复/路由语义、SQLite崩溃顺序错误、SSE与固定Pi不一致以及UI把配置成功误作健康。
通过新包隔离、Fake Provider、16项调试场景和下一阶段114项单元测试控制。正式单元测试刻意作为下一Gate执行，
因此Gate C不能被描述为“测试完成”或“可生产发布”。
