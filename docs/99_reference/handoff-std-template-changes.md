## 0. 一句话任务

`design.system-mechanism`（系统机制设计）当前**缺"分解到模块"的硬章节**，无法承担"作为模块设计输入"的核心用途；
同时存在若干**模板自身错误**（自相矛盾、章节重叠、boilerplate 重复）。
请按下文 P0 修改 `design.system-mechanism` 与 `design.definition`（模块设计），P1/P2 分批跟进。

## 1. 背景：机制设计的用途是"模块设计的输入"

一个功能跨多个模块时，需要**一份文档整体描述该功能，再分解到各模块**（各模块负责什么、必须给别的模块提供什么接口），
模块设计才能据此往下分解到实现与代码文件。LLMTier 的 5 份机制文档写完后发现：**模板没有承载该分解的章节**，
导致机制文档只能描述"系统层面"，无法驱动模块设计。

## 2. 三层承接关系（建议写入 STD 设计标准）

| 层 | 描述什么 | 分解方向 | 剖面 |
|---|---|---|---|
| 系统设计 | 机制要解决的问题 + 大致原理 + 机制清单 | 系统 → 机制清单 | — |
| 系统机制设计 | 机制**详细** + **分解到模块**（各模块负责什么、提供什么接口）| 机制 → 模块 | **纵向**：一机制跨多模块 |
| 模块设计 | 本模块**横切所有机制**的实现设计 + 分解到代码文件 | 模块 → 代码文件 | **横向**：一模块承接多机制 |

- **交叉点**：机制文档"模块分解"章 = **要求侧**；模块设计**附录"机制承接表"** = 承接侧（对照查漏，不约束模块正文组织）。
- 复现判据：机制 §14 四子节列名 **=** 模块设计附录 A 列名。

## 6. 不确定性与反例

- 样本单一（LLMTier 纯软件项目）；四子节对硬件/多 Owner 领域未验证。
- **多 Owner 变体**：机制涉及多 Owner 时，"模块"应替换为"责任单元/Owner"。
- **单模块变体**：机制不跨模块时，§14 应允许写"单模块，无跨模块分解"+ 理由。

## 7. 验收 Gate 与流程

1. **G1**：`system-mechanism` 含 §14 四子节，至少一个样本可填满；
2. **G2**：类别 A 8 项全部修毕（无自相矛盾/重叠/重复）；
3. **G3**：`design.definition` 含"机制承接表"附录，与机制 §14 列对齐；
4. **G4**：一份真实机制文档 + 其模块设计可端到端追溯（要求↔承接）；
5. 分批：**P0 = `system-mechanism` + `design.definition`（含 A 类修复）先行**；P1/P2 随下次 STD 版本。
