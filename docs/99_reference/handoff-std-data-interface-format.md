# HANDOFF：STD 全设计文档「数据结构 / 接口」描述格式统一建议

- 日期：2026-09-24
- 提出方：LLMTier（`corezilla/LLMTier`，branch `docs/std-draft21-upgrade`）
- 接收方：STD 维护方（`/Users/ben/work/STD`，STD `0.1.0-draft.31`）
- 触发：按 `design.definition` 编写 LLMTier 模块设计时，§6 数据模型 / §9 接口与机器契约 逐条落到字段级后的实证
- 证据：`docs/40_module_design/libdiag-design.md` §5.3 / §6 / §9.1 / §9.2（8 个模块设计中的样板）

## 0. 一句话任务

把**数据结构的固定格式**与**接口的固定格式**定义为 STD 通用规范，**所有设计文档**的「数据结构 / 接口」章节统一采用，并按文档类型规定各自应描述的数据结构与接口（见 §3 表）。

## 1. 动机

现状：`design.software-system` / `design.system-mechanism`（§4 数据结构设计、§5 接口设计）/ `design.subsystem` / `design.definition`（§6、§9）/ `design.implementation` / `design.data-dictionary` / `contracts.specification` 都要求描述数据与接口，但**格式各异、粒度不一**，消费方（其它模块的设计、实现与测试用例）无法直接据此编码或写用例。目标：

- 数据结构与接口**分节**，被复用的数据结构**只描述一次**，接口用 ID 引用；
- 每个数据结构、每个接口都有**固定的字段段落**，粒度足够写实现与测试用例；
- 明确**每种设计文档**应描述到何种数据、何种接口，避免重复或越层。

## 2. 两个固定格式

### 2.1 数据结构（固定 4 段）

```markdown
#### <Data ID> · `<名称>`
- **定义**：<一句话语义、用途、边界>
- **字段**：
  - `名称`：`类型`｜必填性（必填 / 可空）｜范围·枚举·单位｜说明
  - ...
- **不变量**：<跨字段约束、默认、唯一性、寿命>
- **来源**：<定义 / 产出该结构的权威位置（文件·symbol 或 schema 路径）>
```

### 2.2 接口（固定 6 段）

```markdown
#### <Interface ID> · `<签名 / 操作名>`
- **功能**：<做什么、为谁、边界>
- **输入**：
  - `名称: 类型`｜必填·默认｜范围·枚举｜说明
  - ...
- **输出**：<数据结构 ID（§数据） / 字节流 / 无>
- **返回值**：<每条件一行：`<条件> → <值>`；含错误码与其触发条件>
- **统计 · 日志**：<对外可见的统计/日志口径与触发；无则写 `无`>
- **数据库**：<何种情况改哪些表/列（或“只读”“无”）；非持久接口写 `无`>
```

- 硬件 / FPGA 设计：结构相同，接口段把 `统计 · 日志` 换为 `时序 · 资源`、`数据库` 换为 `持久化 · 寄存器`；字段行以 `位宽 / 端序 / 复位值` 替代软件类型。
- 时间统一 RFC3339（UTC，毫秒）；`?` 表示可空。

## 3. 每种设计文档应描述的数据结构与接口

| 设计文档（template） | 应描述的**数据结构** | 应描述的**接口** | 粒度 |
|---|---|---|---|
| 架构设计 `design.system` | 平台级**对象/实体的目录索引**（名称、owner、权威文档），不展开字段 | **系统间接口索引**（谁↔谁、方向、权威契约 ID），不展开 wire 细节 | 索引级 |
| 软件系统设计 `design.software-system` | **系统级对外数据对象**（跨系统边界传输的顶层对象：请求/响应信封、事件、资源表示） | **系统边界接口**（对外/跨系统；责任模块 + 权威契约引用） | 跨边界必需字段 |
| 系统机制设计 `design.system-mechanism` | 机制**状态与消息**（状态机状态、消息/事件类型、判定事实、阶段） | **机制参与方交互**（每步的发起/接收方、输入、输出、失败出口） | 机制内部必需 |
| 子系统设计 `design.subsystem` | 子系统**对外暴露的数据对象**（类型、枚举、状态） | **子系统对外接口**（被谁调用、提供/消费、依赖方向） | 子系统边界 |
| **模块/组件设计** `design.definition` | 模块**对外可复用数据结构**（视图/DTO/枚举/开关）：4 段；复用只描述一次 | **模块对外接口**（逐接口 6 段）+ **文件间接口**（门面↔功能） | 字段级（对外） |
| **数据字典** `design.data-dictionary` | **字段级权威**：Entity Catalog、Field Dictionary、Enum/Status/Error、Key/Ownership、序列化、持久化 | 只被接口**引用**，不描述接口 | 字段级（权威） |
| **实现规格（ISD）** `design.implementation` | 模块**内部私有数据**（文件内类型、内存对象、所有权/寿命）、表结构、状态机 | **关键函数实现契约**（完整签名、参数、成功/错误返回、前置条件、副作用、幂等、并发）；对外结构**引用模块设计 ID** | 函数级（私有） |
| 硬件设计 `design.hardware` | 板级**寄存器 / 接口信号 / 时序参数** | 板级**连接器 / 总线协议 / 引脚** | 板级 |
| FPGA 设计 `design.fpga` | RTL **接口信号 / 寄存器 map / 状态** | RTL **模块端口 / 握手协议** | 模块端口级 |
| 接口契约 `contracts.specification` / `interfaces.control` | **机器可读 wire Schema**（字段/类型/必填/范围/编码/版本） | **端点/方法契约**（路径/方法/请求/响应/状态码/错误码） | 字段级（权威） |

## 4. 通用规则

1. **数据结构与接口分节**；被复用结构只在数据结构节描述一次，接口只引用其 ID。
2. **同一对象只有一处字段级 authority**：机器契约（`interfaces/*`）/ 数据字典 是字段权威，设计文档的数据结构**与之一致并引用**，不复制两份。
3. **粒度自外向内**：系统 → 机制 → 子系统 → 模块（对外可复用）→ ISD（内部私有）；越靠内越细，越靠外越粗。
4. 接口的 `返回值` 必须**逐条件**列出（否则消费方无法写用例）；`数据库` 必须写清**何种情况改哪些表/列**。
5. `统计 · 日志` 只在**对外可观察**时写（可观测性/审计口径），内部日志归 ISD。

## 5. 配套设施建议

- 新增 STD 共享 AI 指南（如 `docs/ai-guides/design-data-interface-format.md`）承载 §2 两套固定格式与 §3 表；各模板的「数据结构 / 接口」章节引用该指南。
- 校验器（`validate-design`）：对采用该格式的章节，检查每个数据结构含 4 段、每个接口含 6 段且 `返回值`/`数据库` 非空；字段行/参数行按 `｜` 分列。
- 迁移：先在新模板版本中把两套格式设为推荐，稳定后改为必需。

## 6. 证据（LLMTier 试点）

- `docs/40_module_design/libdiag-design.md`：§9.1 共享数据结构（11 个，4 段）、§9.2 接口规格（15 个，6 段）、§6 数据模型（6 表，4 段）、§5.3 文件间接口（6 段）；一次 correctness review 修正了可空性等 7 处，证明该格式**可对照代码逐项校验**。
